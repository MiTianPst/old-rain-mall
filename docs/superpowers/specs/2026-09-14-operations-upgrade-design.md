# 旧雨电商运营版升级设计

## 1. 背景与目标

旧雨电商当前已经具备商品浏览、认证、购物车、地址簿、结算、订单、模拟支付、心悦会员和后台基础管理能力。本次升级将项目从“可完成交易的 MVP”扩展为可支撑日常运营的单商家自营商城。

本次范围包含：

- 商品 SKU、商品多图和后台图片上传
- 库存流水与库存预警
- 物流信息、运输状态和确认收货
- 售后退款申请、审核和模拟退款
- 后台用户与会员管理
- 修改密码、忘记密码、登录限制和后台操作日志
- 订单备注、筛选和 CSV 导出
- 库存、订单和销售额运营统计

本次明确不做多商家入驻、商家结算、平台佣金、分账和店铺体系。商品、订单、支付和售后均属于旧雨自营商城。

## 2. 设计原则

- 保持当前 Next.js 模块化单体架构，不拆分微服务。
- 页面默认使用 Server Component；表单写入使用 Server Action；对外或浏览器直接调用的能力使用 Route Handler。
- 业务规则集中在 `src/server/services`，数据库访问集中在 `src/server/repositories`，页面不得复制库存、价格、会员或状态流转规则。
- 所有金额继续使用整数分，所有库存变更必须在事务中完成并写入流水。
- 管理后台的每个读写入口都在服务端重新检查管理员身份，不能依赖隐藏按钮或前端角色字段。
- 面向用户的文案使用中文，必要的代码注释使用中文。
- 本地开发图片保存到 `public/uploads`，通过独立存储接口隔离；生产环境可替换为对象存储而不改变业务接口。
- 继续使用归档和隐藏代替商品、分类的硬删除；订单和售后历史不可被普通管理操作破坏。

## 3. 分期范围

### 第一期：商品与库存

#### 3.1 SKU

现有 `products` 继续作为商品主记录（SPU）。新增 `product_variants`：

- `id`、`product_id`、`sku_code`
- `name`（规格组合名称）
- `attributes_json`（颜色、尺寸等规格键值）
- `price_cents`、`stock`、`status`
- `created_at`、`updated_at`

商品至少保留一个默认 SKU。购物车和订单项从 `product_id` 改为记录 `variant_id`；订单项同时保存 SKU 名称、单价和规格快照，保证历史订单不受商品后续编辑影响。

商品公开 API、详情页和后台表单都以 SKU 为最终价格和库存来源。没有规格的旧商品迁移为默认 SKU，保持现有 URL 和数据可用。

#### 3.2 多图与上传

继续使用 `product_images`，补充主图标识和排序约束。新增上传 Route Handler：

- 仅允许 JPEG、PNG、WebP
- 单文件大小限制为 5 MB
- 文件名不信任，服务端生成随机文件名
- 只写入项目 `public/uploads/products`
- 返回站内绝对路径，不接受客户端伪造的数据库对象

后台商品编辑页支持上传、删除和排序；商品详情优先显示主图，再显示其余图片。上传失败只返回中文错误，不暴露文件系统路径。

#### 3.3 库存流水

新增 `inventory_transactions`：

- `variant_id`
- `type`：`INITIAL`、`INBOUND`、`SALE`、`CANCEL_RESTORE`、`REFUND_RESTORE`、`ADJUSTMENT`
- `quantity_delta`、`stock_before`、`stock_after`
- `reference_type`、`reference_id`、`operator_user_id`、`note`
- `created_at`

下单扣减、取消恢复、退款恢复和后台调整必须在同一事务中更新 SKU 库存并写流水。库存不足采用条件更新，避免超卖。后台商品列表显示库存预警标记，预警阈值默认 10，可在后台配置前保留为系统常量。

### 第二期：物流与售后

#### 3.4 物流

新增 `shipments`：

- `order_id`（一单一物流记录）
- `carrier`、`tracking_no`
- `status`：`PENDING`、`SHIPPED`、`IN_TRANSIT`、`DELIVERED`
- `shipped_at`、`delivered_at`
- `created_at`、`updated_at`

管理员只能对已支付订单发货，录入物流公司和单号后订单进入 `SHIPPED`。本项目暂不接第三方物流查询，运输中和已送达由后台模拟更新；用户可查看物流快照并确认收货。确认收货只允许已发货或运输中的订单执行。

#### 3.5 售后与退款

新增 `after_sales`：

- `id`、`order_id`、`user_id`
- `reason`、`description`
- `status`：`REQUESTED`、`APPROVED`、`REJECTED`、`REFUNDING`、`REFUNDED`
- `refund_amount_cents`
- `review_note`、`reviewed_by`、`reviewed_at`
- `refunded_at`、`created_at`、`updated_at`

第一版按订单维度申请售后，退款金额不得超过订单实付金额；每个订单最多存在一个有效售后单。用户只能申请自己的已支付、已发货或已完成订单，取消、关闭和已退款订单不能重复申请。

管理员审核通过后执行模拟退款：支付记录标记为退款完成、订单进入 `REFUNDED`，退款商品数量恢复库存并写 `REFUND_RESTORE` 流水。退款和库存恢复必须在同一事务中完成，并通过唯一约束保证重复点击不会重复退款。

### 第三期：用户、安全与运营

#### 3.6 用户与会员管理

新增用户状态字段 `ACTIVE`、`FROZEN`。后台提供：

- 用户搜索、角色和状态筛选
- 查看累计实付、心悦等级和会员升级流水
- 冻结/解冻普通用户
- 查看用户订单摘要

被冻结用户不能新增购物车、提交订单、支付或申请售后；已有订单仍可被读取。管理员不能冻结自己，不能通过普通表单修改累计实付和会员等级。

#### 3.7 账号安全

- 修改密码要求当前密码校验，新密码至少 8 位。
- 忘记密码生成一次性、限时重置令牌；生产接入邮件服务前，本地开发仅通过服务端日志验证流程，不在公开页面展示令牌。
- 登录和密码重置按 IP 与账号维度做轻量频率限制。
- 登录错误继续使用统一提示，不泄露邮箱是否存在。
- 所有管理员写操作写入 `audit_logs`，记录操作者、动作、目标类型、目标 ID、摘要和时间。

#### 3.8 订单运营能力

订单增加管理员备注字段，后台支持按订单号、用户邮箱、状态和时间筛选，并提供当前筛选结果的 CSV 导出。导出只包含订单运营所需字段，不包含密码、Session、支付密钥等敏感信息。

#### 3.9 运营看板

后台概览新增：

- 今日订单数和今日销售额
- 待支付、待发货、售后处理中的订单数
- 当前低库存 SKU 数
- 最近订单列表

统计全部从服务端按数据库查询计算，不将客户端传入的时间范围或金额作为可信条件。默认时间范围为当天，时间边界使用项目统一时区处理。

## 4. 订单与状态设计

订单主流程扩展为：

```text
PENDING_PAYMENT -> PAID -> SHIPPED -> IN_TRANSIT -> DELIVERED -> COMPLETED
        +----> CANCELLED
        +----> CLOSED（超过两小时）

PAID / SHIPPED / IN_TRANSIT / DELIVERED / COMPLETED -> REFUNDED（售后）
```

约束如下：

- `PENDING_PAYMENT` 超过两小时进入 `CLOSED` 并恢复库存。
- 只有 `PAID` 可以发货；只有 `SHIPPED` 或 `IN_TRANSIT` 可以确认收货。
- 售后审核和退款必须验证订单当前状态、申请人和退款金额。
- 每个状态转换由服务层定义允许的前置状态，并在数据库事务中条件更新。
- 订单项保存 SKU、商品名称、图片、规格、单价和数量快照。

支付状态增加 `REFUNDED`，退款完成后支付记录与订单售后记录保持一致；退款不再次累计会员消费金额。

## 5. 数据流与权限

公开浏览只读取 `ACTIVE` 分类、`ACTIVE` 商品和 `ACTIVE` SKU。购物车、结算、订单、地址和售后先通过当前 Session 取得用户 ID，再由仓储层按用户 ID 过滤。后台读写统一经过 `requireAdmin`，用户管理的冻结状态在服务层二次校验。

文件上传先经过 MIME、大小和扩展名校验，再写入受限目录；数据库只保存站内 URL。CSV 导出由服务端生成并设置下载响应头，不拼接未校验的 SQL 或文件路径。

## 6. 错误处理

- 输入错误返回 Zod 中文错误。
- 未登录返回登录跳转或 401；无权限返回 403；资源不存在统一返回 404。
- 状态冲突返回可识别的业务代码和中文提示，前端刷新服务端数据后再展示。
- 事务失败回滚所有关联写入，不返回数据库堆栈。
- 上传失败、导出失败和限流均返回安全的统一错误。

## 7. 测试与验收

每一期至少覆盖：

- Schema 输入白名单、金额和状态转换
- SKU 价格、库存扣减、取消/退款恢复和重复操作幂等
- 普通用户与管理员权限边界、冻结用户限制
- 售后金额上限与订单状态约束
- 图片 MIME、大小和文件名安全校验
- CSV 导出不包含敏感字段

完成每一期后运行：

```bash
npm test
npm run test:db
npm run lint
npm run typecheck
npm run build
```

数据库变更必须生成新的 Drizzle migration，并在本地 MySQL 上执行迁移和回归测试。验收数据使用临时账号和临时商品，结束后清理并恢复库存。

## 8. 交付顺序

1. 第一期：SKU、图片上传、多图管理、库存流水和库存预警。
2. 第二期：物流记录、运输状态、确认收货、售后申请和模拟退款。
3. 第三期：用户/会员后台、账号安全、审计日志、订单运营和统计看板。

每期独立完成迁移、页面、Server Action/Route Handler、服务层、仓储层、测试和文档更新；不在同一迁移中混入下一期未实现的业务状态。
