# 地址簿、结算、订单与模拟支付设计

## 目标

为旧雨电商实现登录用户从维护收货地址、确认购物车、创建订单、取消或关闭待支付订单，到完成模拟支付和升级心悦会员的完整交易闭环。第一版全部包邮，待支付订单有效期为两小时，并通过可替换的支付适配器为后续接入微信支付或支付宝保留清晰边界。

## 范围

- 收货地址簿：新增、编辑、删除、设为默认地址，每个用户最多保存 20 条。
- 结算页：选择收货地址，展示当前购物车、会员等级、折扣、优惠和应付金额。
- 创建订单：服务端重新校验地址、商品、分类、库存、价格和会员等级。
- 用户订单：订单列表、订单详情、取消待支付订单。
- 订单过期：创建两小时后关闭仍未支付的订单并恢复库存。
- 模拟支付：点击后模拟成功，通过统一支付确认事务更新订单、支付和会员数据。
- 心悦会员：支付成功后累计实付金额，按累计门槛升级并记录升级流水。

本阶段不实现真实支付渠道、退款、售后、物流轨迹、优惠券、地址智能解析、地区运费和后台订单管理。

## 技术与约束

- Next.js `16.3.5`、React `19.2.8`、TypeScript `5.9.3` 严格模式、Tailwind CSS `4.3.3`。
- Drizzle ORM `0.45.2`、Drizzle Kit `0.31.10`、mysql2 `3.24.4`、MySQL `8.4`。
- 页面默认使用 Server Component；交互表单使用 Client Component 和 Server Action。
- Route Handler 只用于未来支付回调和订单过期任务等外部入口。
- 所有金额使用整数分，折扣使用整数基点，禁止用浮点元参与计算。
- 所有用户可控输入使用 Zod 校验；服务端重新鉴权并校验资源所有权。
- 数据库结构变更通过 Drizzle 生成迁移并实际执行，不使用 `db:push` 代替可追踪迁移。

## 模块边界

```text
地址页面 / 结算页面 / 订单页面 / Server Actions
  -> 地址服务 / 订单服务 / 支付服务
    -> 地址仓储 / 订单仓储
      -> MySQL 事务

支付服务
  -> PaymentProvider 接口
    -> MockPaymentProvider（本阶段）
    -> 微信或支付宝适配器（后续）

支付确认事务
  -> 会员规则函数
    -> 用户累计实付与会员升级流水
```

地址、订单和支付各自保持独立职责。页面不复制金额、库存、状态转换或会员升级规则。支付渠道只负责创建支付请求和验证结果，订单支付成功后的数据库变更统一由支付确认事务完成。

## 数据模型

### 收货地址

新增 `user_addresses` 表：

- `id`：无符号自增整数主键。
- `userId`：关联 `users.id`，用户删除时级联删除地址。
- `recipientName`：收货人姓名，最长 100 字符。
- `recipientPhone`：手机号，最长 32 字符。
- `province`、`city`、`district`：省、市、区，分别最长 100 字符。
- `detailAddress`：详细地址，最长 500 字符。
- `label`：地址标签，可空，最长 50 字符。
- `isDefault`：是否为默认地址，默认 `false`。
- `createdAt`、`updatedAt`：创建和更新时间。

为 `userId` 和 `(userId, isDefault)` 建立查询索引。MySQL 不使用部分唯一索引表达“每个用户最多一个默认地址”，该约束由事务服务维护。

地址规则：

- 用户只能读取和修改自己的地址。
- 每个用户最多保存 20 条地址。
- 第一条地址自动成为默认地址。
- 设置默认地址时，在同一事务内取消该用户原默认地址并设置新默认地址。
- 删除默认地址后，在同一事务内将最近更新的剩余地址设为默认；没有剩余地址时不设置。
- 订单复制地址快照，后续编辑或删除地址不影响历史订单。

### 订单与支付

复用现有 `orders`、`order_items`、`payments` 和 `membership_level_logs` 表。`payments` 增加可空且唯一的 `providerTradeNo` 字段，用于未来保存支付平台交易号；模拟支付可以为空。

订单保存下单时的会员等级、折扣基点、商品原价、会员优惠、运费、实付金额和收货信息快照。支付单保存商城支付单号、订单、渠道、金额、状态和支付时间。每个订单只有一条支付记录，通过 `payments.orderId` 唯一索引保证。

## 地址簿交互

- `/addresses` 展示当前用户全部地址，并提供新增、编辑、删除和设为默认操作。
- `/addresses/new` 新增地址；`/addresses/[id]/edit` 编辑当前用户拥有的地址。
- 未登录访问地址页面时跳转 `/login?next=<当前路径>`。
- 结算页只允许选择当前用户地址簿中的地址，不接受客户端直接提交完整地址快照。
- 删除操作使用明确的确认交互；操作成功后刷新地址列表和结算页。
- 地址列表按默认地址优先、更新时间倒序排列。

## 金额与会员规则

会员等级和折扣集中维护在 `src/lib/membership.ts`：

| 等级 | 累计实付门槛 | 折扣基点 |
| --- | ---: | ---: |
| 普通会员 | 0 分 | 10000 |
| 心悦 1 级 | 800000 分 | 9800 |
| 心悦 2 级 | 8000000 分 | 9500 |
| 心悦 3 级 | 80000000 分 | 9000 |

创建订单时使用用户当前等级计算折扣：

```text
originalAmountCents = 所有订单项的 unitPriceCents × quantity 之和
discountedMerchandiseCents = floor(originalAmountCents × discountRateBps / 10000)
memberDiscountCents = originalAmountCents - discountedMerchandiseCents
shippingFeeCents = 0
totalCents = discountedMerchandiseCents + shippingFeeCents
```

达到升级门槛的当前订单仍使用支付前等级。支付成功后把该订单 `totalCents` 加入 `lifetimePaidCents`，根据新累计金额一次性升级到符合条件的最高等级，折扣从下一笔订单开始生效。只有等级发生变化时才写 `membership_level_logs`。

## 创建订单事务

`createOrder` 只接收当前用户 ID 和地址 ID，不接收客户端价格、折扣、会员等级或订单总额。

事务内按以下顺序执行：

1. 锁定并读取用户，取得会员等级和累计实付金额。
2. 读取当前用户拥有的地址；不存在时拒绝下单。
3. 锁定用户购物车条目及相关商品，并按商品 ID 稳定排序以降低死锁风险。
4. 确认购物车非空、商品为 `ACTIVE`、所属分类为 `ACTIVE`、数量为正且库存充足。
5. 使用数据库中的商品价格和用户当前会员等级计算订单金额。
6. 以 `stock >= quantity` 为条件扣减每件商品库存；任一扣减失败则整个事务回滚。
7. 创建 `PENDING_PAYMENT` 订单，`expiresAt` 为数据库当前时间之后两小时。
8. 创建订单商品快照和 `PENDING` 模拟支付记录。
9. 删除本次已转换为订单的购物车条目。
10. 返回订单号，由页面跳转到订单详情。

订单号和支付单号由服务端生成，包含时间成分和安全随机值，长度不超过现有 32 字符字段。唯一索引冲突时可在事务外有限重试生成编号，但不得重复扣减库存。

## 取消与过期

用户只能取消自己状态为 `PENDING_PAYMENT` 的订单。取消事务锁定订单和订单项，通过条件更新把状态改为 `CANCELLED`、写入 `cancelledAt`，随后恢复订单项库存。状态已经改变时不得再次恢复库存。

订单创建两小时后仍未支付则进入 `CLOSED`：

- `/api/jobs/expire-orders` 作为批量关闭入口，使用服务端任务密钥鉴权，分批处理过期订单。
- 用户打开订单列表、订单详情或尝试支付时，也会处理相关已过期订单，保证本地没有定时任务时仍能释放库存。
- 关闭操作锁定订单并只允许 `PENDING_PAYMENT -> CLOSED`，恢复库存和状态修改位于同一事务。
- 已支付、已取消或已关闭订单不会恢复库存。

## 模拟支付与未来真实支付

支付渠道遵循可替换接口：

```ts
interface PaymentProvider {
  createPayment(order: PaymentOrder): Promise<PaymentCreation>;
  verifyCallback(payload: unknown): Promise<PaymentResult>;
}
```

本阶段的 `MockPaymentProvider` 在用户点击模拟支付后返回成功结果。支付服务不直接信任页面传入金额，只根据订单号读取支付单并进入统一确认事务。

支付确认事务：

1. 锁定当前用户拥有的订单、对应支付单和用户记录。
2. 已成功支付时返回原结果，保持幂等。
3. 订单已过期时关闭订单、恢复库存并拒绝支付。
4. 仅允许 `PENDING_PAYMENT` 订单和 `PENDING` 支付单继续。
5. 校验支付金额与订单 `totalCents` 一致。
6. 更新支付单为 `SUCCESS` 并写入 `paidAt`。
7. 更新订单为 `PAID`、支付状态为 `SUCCESS` 并写入 `paidAt`。
8. 将订单实付金额累加到用户 `lifetimePaidCents`。
9. 计算新会员等级；发生升级时更新用户等级、升级时间并写入一条升级流水。

未来接入微信或支付宝时，新增对应 `PaymentProvider` 实现和回调 Route Handler。回调必须验签、核对商户订单号与金额，再调用同一个支付确认事务；订单、库存和会员逻辑无需复制。

## 页面与路由

- `/addresses`：地址列表与管理入口。
- `/addresses/new`：新增地址。
- `/addresses/[id]/edit`：编辑地址。
- `/checkout`：选择地址并展示商品、会员折扣与应付金额。
- `/orders`：当前用户订单列表，按创建时间倒序。
- `/orders/[orderNo]`：订单详情、状态、地址快照、商品快照、金额和允许的操作。
- `/api/jobs/expire-orders`：带任务密钥鉴权的过期订单批处理入口。

创建、取消、模拟支付以及地址写操作优先使用 Server Action。Server Component 通过服务层直接读取数据，不请求本项目自己的 Route Handler。

## 错误处理与安全

- Server Action 和 Route Handler 每次都重新获取 Session，绝不接受客户端提交的 `userId`。
- 地址 ID、订单号和表单字段统一通过 Zod 校验。
- 地址和订单查询始终带当前用户 ID，避免越权读取或修改。
- 下单事务任一步失败都会回滚，库存、订单、支付和购物车不会处于部分成功状态。
- 库存不足时返回具体商品名称；商品下架、分类隐藏、地址不存在、购物车为空和订单状态冲突返回中文业务错误。
- 数据库异常写服务端日志，但不记录 Cookie、Session、地址全文、手机号、支付载荷或连接串。
- 过期任务入口使用单独环境变量密钥，不与认证密钥或数据库密码复用。
- 模拟支付按钮只影响当前登录用户自己的订单；已过期订单绝对不能支付。

单元测试覆盖：

- 地址表单校验、20 条上限、首条默认、切换默认和删除默认后的继任规则。

- 模拟支付成功、重复支付幂等、金额不一致、过期拒付和会员升级。

MySQL 集成测试覆盖：

- 地址默认规则在真实事务中的一致性。
- 创建订单同时扣库存、写订单与快照、创建支付单并清空购物车。
- 下单失败时完整回滚。
- 取消和关闭订单只恢复一次库存。
- 重复模拟支付只累计一次实付金额并最多写一条升级流水。
- 大额订单可以直接升级到符合条件的最高心悦等级。

页面验收覆盖：

- 登录用户完成地址新增、加入购物车、选择地址、创建订单、模拟支付和查看会员升级结果。
- 未登录访问受保护页面会跳转登录。
- 其他用户无法读取或操作当前用户的地址与订单。
- 中文文案、移动端布局、空状态、加载状态和错误反馈可正常使用。

完成后运行 `npm test`、MySQL 集成测试、`npm run lint`、`npm run typecheck` 和 `npm run build`，并使用本地 MySQL 实际走通完整交易流程。
